AI enablement: improving prompting and evaluating outputs across LLMs with Vellum

Case study · LLM evals

Enablement AI

Teaching a teammate how to systematically iterate on prompts and compare outputs across multiple LLMs in Vellum.

The challenge

Odyseek is a career agent, and I was building it as the engineer. But the domain knowledge sat with Cat, our CEO: as an experienced hiring manager, she knew exactly what the agent’s outputs should look like, and she could tell within seconds when they were wrong. The problem was that her workflow for acting on that knowledge lived in a single chat window: tweak the prompt, reread the output, tweak again. It felt productive, but nothing accumulated. There was no record of which version performed better, no way to compare models side by side, and every evaluation ran through the same resource: Cat herself, rereading outputs and judging them from experience.

For a career agent, where output quality directly affects decisions about people’s careers, gut feel isn’t a quality bar. Cat’s expertise was the evaluation layer, and as long as testing a prompt properly required an engineer in the loop, that layer had no way to scale. She needed evidence, and she needed to generate it herself.

How we set up Vellum

Rather than hand Cat a tool and a login, I walked her through a repeatable workflow for treating prompts like something you can actually test:

  1. Structure the prompt as an artifact. We moved the prompt out of the chat window and into a workflow with defined inputs, so every run used a versioned prompt against real data instead of a fresh paraphrase from memory.
  2. Build a small test set. A set of real cases from the agent’s actual usage became the baseline. Now “is this prompt good?” had a fixed yardstick instead of whatever output happened to come back that day.
  3. Run side-by-side comparisons. With the test set in place, Cat could run the same inputs across models from different providers and see the differences in one view, instead of pasting the same prompt into a row of chat tabs and squinting.
  4. Score the outputs. Cat’s judgment became the evaluation criteria: what she’d been checking by instinct as a hiring manager got written down as the bar every output is measured against, so model choice and prompt changes became decisions she could defend, not coin flips.

The key shift wasn’t technical. Cat never needed to become an ML engineer, and I never needed to sit between her and the evidence. She needed the loop to be tight enough that iterating felt like testing, not guessing, and after the initial walkthrough she could run the whole loop herself.

Outcome

The most concrete change: Cat went from waiting on an engineer to test every prompt to running the full cycle independently. Structure the prompt, run the test set, compare models, score the outputs. Every change is on the record, and every prompt decision comes with a reason attached.

The confidence is the real outcome. When output quality is your responsibility and you can’t explain why a prompt works, you’re one unexplainable regression away from losing trust in the whole pipeline. Cat’s workflow now has an answer for “why this one?” for every prompt she ships.
